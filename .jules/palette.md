## 2024-05-22 - Accessibility for Dynamic Notifications
**Learning:** Toast notifications (dynamic content updates) are silent to screen readers unless wrapped in a container with `aria-live="polite"` and `aria-atomic="true"`.
**Action:** Always wrap dynamic notification areas with these attributes. Ensure close buttons in these notifications have `aria-label`.

## 2024-05-22 - Keyboard Shortcut Discoverability
**Learning:** Keyboard shortcuts are powerful but invisible. Adding them to `title` attributes (e.g., "Print (Ctrl+P)") and using `aria-keyshortcuts` makes them discoverable and accessible to screen reader users without cluttering the UI.
**Action:** When implementing keyboard shortcuts, always update the UI element's `title` and add `aria-keyshortcuts`.

## 2024-05-22 - Focus Style Specificity Override
**Learning:** CSS specificity conflicts between custom component classes (e.g., `.upload-box`) and utility classes (e.g., Tailwind's `bg-yellow-300`) can prevent focus styles from applying correctly. In this case, `.upload-box` defined a background color that overrode the focus utility.
**Action:** Used `!important` modifiers (e.g., `focus:!bg-yellow-300`) to ensure accessibility focus styles are visible and take precedence without requiring a full refactor of the existing CSS architecture.

## 2026-02-16 - Dynamic Toast Roles
**Learning:** Using `role="alert"` for all toasts is aggressive. Errors should use `role="alert"` (assertive), while success/info messages should use `role="status"` (polite) within an `aria-live="polite"` container.
**Action:** Dynamically assign roles based on message type in notification components.

## 2026-02-16 - Form Accessibility: Label Association
**Learning:** Visual proximity of labels to inputs does not guarantee accessibility. Missing `for` attributes on `label` elements breaks screen reader announcements and click-to-focus behavior.
**Action:** Always verify label associations using automated tools or by clicking the label to ensure focus shifts to the input.

## 2026-06-25 - Accessibility of Dynamic Elements
**Learning:** Dynamic elements (like pages generated by JS) often miss ARIA labels, making them invisible to screen readers. Always verify accessibility attributes for dynamically created DOM elements.
**Action:** When creating elements with `innerHTML`, check for `aria-label`, `role`, and keyboard accessibility (`tabindex`, focus styles).

## 2025-02-16 - Accessible Toolbar Keyboard States and Labels
**Learning:** In dynamically generated grid layouts with absolute positioned toolbars (`absolute top-2 right-2`), `group-hover:opacity-100` makes toolbars visible on mouse hover, but completely hides them from keyboard-only users who tab to the internal buttons. Furthermore, duplicated HTML structures (like `cell.innerHTML`) risk inconsistent accessibility attributes (e.g. `aria-label`, `aria-hidden` on ligatures) across different layout generators.
**Action:** Use `focus-within:opacity-100` on the absolutely positioned parent container so the entire toolbar becomes visible when any of its child buttons receive focus. Centralize duplicated HTML into a single constant (e.g., `PAGE_TOOLBAR_HTML`) to ensure accessibility attributes are applied consistently across all generated views, and inject context-aware labels (e.g., `aria-label="Zoom Cover"`) via the initial rendering or setup function (`setupToolbar`).

## 2026-03-23 - Status Element Accessibility and Contrast
**Learning:** Dynamically updated status text elements (like an upload progress indicator) must have `aria-live="polite"` to be announced by screen readers when their text content changes. Additionally, using low contrast text colors (like `text-gray-400` or `text-red-500` on light backgrounds) fails WCAG AA guidelines, and should be updated to high contrast combinations (e.g., `text-gray-600` or `bg-red-600 text-white`) for readability.
**Action:** Always add `aria-live` attributes to static DOM nodes that receive dynamic text updates conveying status, and verify color contrast ratios for all dynamic states, especially error messages.

## 2026-03-30 - Accessible Progress Bars
**Learning:** Visual progress bars (like CSS width-based indicators) are invisible to screen readers unless they use `role="progressbar"` and dynamically update `aria-valuenow`.
**Action:** Always add these ARIA attributes to custom progress indicators and ensure the JavaScript updating the visual progress also updates `aria-valuenow`.

## 2026-10-25 - Accessible Loading States for Buttons
**Learning:** During long-running tasks, simply disabling a button or changing its visual content is insufficient for screen readers. Users need an explicit signal that a background process is active and blocking interaction.
**Action:** When creating inline loading states, always set `aria-busy="true"` on the element alongside visual feedback like inline SVG spinners. Ensure the original button state and attributes are restored in a `finally` block to prevent the UI from getting permanently stuck in an inaccessible state if the task fails.
